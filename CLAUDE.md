## Architecture

React 19 + Vite portfolio site for a cinematographer/colorist. Currently only the **Homepage** is built.

- `src/App.jsx` — renders `Home` only.
- `src/pages/Home/Home.jsx` — the homepage. Contains a fullscreen `VideoBackground` with an SVG-based title, a subtitle ("role") text, and a `Menu`.
- `src/components/VideoBackground/VideoBackground.jsx` — reusable fullscreen `<video autoPlay muted loop playsInline>` background with a dark gradient overlay and a `children` slot (`video-background__content`) laid out as a flex column (`justify-content: space-between`) so the title/subtitle sit at the top and the `Menu` sits at the bottom.
- `src/components/Menu/Menu.jsx` — vertical nav menu (`Featured Work` / `Photography` / `Information`), anchored bottom-right via `align-self: flex-end` on its root `<nav className="menu">`.
- `src/components/ThemeToggle/ThemeToggle.jsx` — a small 3D theme-switcher control, bottom-left on every section. See "Theme toggle" below — currently a live comparison harness, not yet wired to an actual site theme.
- `public/videos/showreel.mp4` — the background video (see `public/videos/README.md` for how to replace it).
- `public/img/` — static images referenced by src path (e.g. `/img/cine.jpg`), same convention as `public/videos/`. Currently holds only `cine.jpg`, used as a placeholder across all of the Featured Work / Photography / Information hover reveals (see below) until real per-section photos are dropped in with their expected filenames.

### Title rendering technique

The name title is not plain HTML text — it's an inline `<svg>` with a `<text>` element using `textLength="950"` on a `viewBox="0 0 1000 115"` (with `textAnchor="middle"`, `lengthAdjust="spacingAndGlyphs"`) so the rendered text always spans exactly 95% of its container width, centered, regardless of font or screen size. The `<svg>` itself is `width: 100%`; the 95%/2.5%-inset math happens entirely inside the SVG coordinate system so the title's left edge lines up with the subtitle's left edge (`.home__role--below`, also `width: 95%`).

### Finalized design decisions

After A/B-testing several options live in the browser, the homepage design is locked in:
- Title font: **Bebas Neue** (`TITLE_FONT_FAMILY` in `Home.jsx`)
- Subtitle font: **Fraunces** (`SUBTITLE_FONT_FAMILY`)
- Subtitle layout: below the title (not the bottom-left-corner alternative that was tried)
- Entrance animation: whole-title fade+blur (`home-fade-in` keyframe: `opacity`+`filter: blur()`, `cubic-bezier(0.33, 0, 0.2, 1)`), title takes 3s, subtitle starts partway through at `SUBTITLE_DELAY_MS` (1.5s — deliberately overlapping the tail of the title's animation rather than waiting for it to fully finish, per user feedback that a full wait felt sluggish)

`index.html` loads Bebas Neue, Fraunces (Google Fonts) and General Sans (Fontshare) — the fonts actually used by `Home.jsx` (title/subtitle) and `Menu.jsx` respectively. During exploration, 6 fonts and 8 different entrance effects (letter-by-letter, whole-fade, spring overshoot, clip-path wipe, per-word split, light-sweep glint, stroke line-draw) were compared for the title through a temporary on-page button harness — that harness has since been removed from `Home.jsx`/`Home.css`, which now only contain the winning combination.

### Menu.jsx — finalized, with one alternate animation kept in reserve

`Menu.jsx` also went through the same kind of live on-page comparison (font, line/divider style, 7 entrance animations) before being locked in:
- Font: **General Sans**
- Line style: thin line above each item, rendered as a real `<span className="menu__item-line">` (not a `border-top`, so it can be dynamically hidden/repositioned for the hover effect below)
- Entrance animation: **`slide-right`** (see below) — the `ANIMATION` constant at the top of `Menu.jsx` controls which one plays; it auto-plays on every page load/refresh, no button needed, driven purely by CSS `animation-delay` timed off `MENU_START_DELAY_MS`

The **`letters-color`** animation (a line draws in per item while its text fills from a hollow outline to solid white — see below) was tried first and is deliberately still implemented in full in `Menu.css`/`Menu.jsx`, kept in reserve at the user's explicit request rather than deleted. The `ANIMATION` constant can be flipped between `'slide-right'` and `'letters-color'` to switch which one is live — both are fully functional. The other animations tried and discarded (whole fade+blur, per-item stagger, clip-path wipe, spring overshoot) and the other line styles (thick/dashed/short-accent/boxed/numbered/minimal) and fonts (Bebas Neue/Fraunces/Archivo Black/Space Grotesk as menu options) were fully removed, not kept.

**How the reserved `letters-color` animation works** (in case it gets switched back on): for each menu item, a horizontal line (`.menu__line-anim`) draws in right-to-left (`transform-origin: right`, `scaleX`) *simultaneously* with that item's text appearing as a hollow outline (`-webkit-text-stroke`, `color: transparent`), then each letter's fill color animates transparent→white over `LETTER_COLOR_DURATION_MS` (1.5s, deliberately slow so the fill is clearly visible) with a `LETTER_COLOR_STAGGER_MS` (25ms) offset per letter. `getLetterColorItemDelays()` computes, per item, when its line/text starts and chains items back-to-back with **zero** gap (`LETTER_COLOR_ITEM_GAP_MS = 0`) — no dead pause between one item finishing its fill and the next item's line starting. The easy mistake when tuning this (made once already): don't let the per-letter fill duration leak into the cumulative start-time math between items — it should only affect how slow the color transition *looks*, never when the next item begins.

Menu animations key off `MENU_START_DELAY_MS` (2600ms), matching exactly when the title+subtitle intro (`Home.jsx`) finishes, so the menu continues that sequence rather than starting fresh.

### Menu item hover — line-grow + reveal effect (photos now in, interaction solid)

On hovering any of the 3 menu items, that item's divider line grows out (animating smoothly from where the default line already starts, not snapping), and a reveal container appears filling the space below down to near the viewport bottom. The photo part that was previously deferred is now implemented for all 3 items (see "Reveal container contents" below).

**Current spec (as of 2026-07-07):**
- **Featured Work (index 0):** line grows all the way to the screen's right edge (`right: 0`, target `left: 46vw` via `REVEAL_VW`).
- **Photography / Information (index 1, 2):** line only grows a small, fixed amount — `frozenPos.left - SECONDARY_GROW_PX` (currently 60px) — not out to the reveal container's edge and not out to `REVEAL_VW`. This went through several rounds of correction (first tried "stop at container edge", then a `SECONDARY_GROW_VW` percentage, both replaced) — treat `SECONDARY_GROW_PX` as the current approach, tune the constant, don't reintroduce the container-edge-based `right` calc without being asked.
- **The reveal container** always matches **"Featured Work" (item 0)'s own position** (`featuredPos`, measured from `lineRefs.current[0]` on every hover, regardless of which item triggered it) — the block appears in the exact same place/size no matter which of the 3 items is hovered. Each item renders its **own separate `<div className="menu__featured-reveal menu__featured-reveal--{index}">`** (not one shared/repositioned div), so each can be styled/animated differently. All 3 are `background: transparent` now that real content fills them — the `--0`/`--1`/`--2` debug colors (terracotta/blue/green) are still defined in `Menu.css` history/muscle-memory but commented out in spirit; if asked to "show me where the containers are," temporarily flip these back to their old solid colors (`#a8593f`/`#3f6ea8`/`#4a8f6b`) to debug, then remember to revert to `transparent` after — this has already been asked for and reverted once.
- Gaps around the reveal container (`REVEAL_GAP_TOP_PX`/`RIGHT_PX`/`BOTTOM_PX` in `Menu.jsx`): **12 / 70 / 24px** (top/bottom were reduced from 24/48 on 2026-07-07 per user request to make the panels a bit taller).
- `.menu` width (`Menu.css`) is `clamp(260px, 30vw, 480px)` (narrowed from `clamp(320px, 34vw, 620px)` on 2026-07-07) — deliberately made narrower so the text column sits further right and the reveal panels (whose right edge is anchored to the text column's position) get more width. Don't widen this back without being asked; it directly trades reveal-panel width for menu-text width.

**The item-to-item animation bug is fixed** — architecturally, not just patched. The earlier bug (switching hover directly between items made the line jump instead of animate) was traced to all 3 items sharing ONE mutable state (`isFixed`/`isActive`/`frozenPos`), so switching items raced/clobbered that shared state before the "frozen" frame could paint. Two attempts at patching that shared-state version (a session-counter ref, then a `useLayoutEffect` forced-reflow) both failed. The fix that actually worked: **give each item its own fully independent hook instance.** `useHoverReveal(getFeaturedRect, exitDelayMs)` is a custom hook encapsulating all of the isFixed/isActive/isLeaving/frozenPos/featuredPos state + handlers + the forced-reflow `useLayoutEffect`; it's called exactly 3 times unconditionally (`hover0`, `hover1`, `hover2` — stable hook-call order, required by the rules of hooks) so each item has its own isolated state that can't interfere with another item's. If touching this again and something seems to regress, check whether a future edit accidentally reintroduces shared state across items — that was the root cause.

**Disabled below 1180px — covers phone AND tablet, fixed/extended 2026-07-14.** `REVEAL_VW` (46) is an absolute vw target, calibrated for wide desktop viewports where the menu is a small fraction of the screen. On narrow viewports the menu's own min width (260px) eats most of the screen, so `frozenPos.left` (Featured Work's line) ends up *smaller* than `REVEAL_VW`'s pixel value — meaning the "grow" target sits to the *right* of the resting position, so the line visibly shrank instead of growing (first reported as "the line decreases instead of growing" for Featured Work specifically; Photography/Information didn't show it since their `SECONDARY_GROW_PX` growth is always relative to their own resting position, not an absolute vw target, so it can't invert). Digging further: even fixing just the line's direction wouldn't have been enough — the reveal panel's own `left`/`right` formula (`right` derived from `featuredPos.left - REVEAL_GAP_RIGHT_PX`, independent of `REVEAL_VW`) crosses over and produces a zero/negative-width panel below roughly 611px viewport width, and stays cramped (well under half of the ~487px desktop width) all the way through the tablet range, since there's structurally not much room to the menu's left at those widths. The gate was first set to 768 (phone only), then explicitly widened to cover tablet too: a finger tap can't *sustain* a hover state at all (the browser fires a synthetic `mouseenter` right before the click, purely as a compatibility shim — a tablet user can never actually "hover" with a finger the way a mouse user can), so the cramped panel would only ever flash before navigating, not be usable, on the vast majority of tablets (finger-only; a tablet with an attached trackpad/mouse is the exception, not the norm). Given all of that, the whole hover-reveal interaction (a desktop mouse pattern) is now gated off below `HOVER_REVEAL_MIN_VIEWPORT_PX` (**1180**, matching the top of the tablet breakpoint in `Menu.css`/`Home.css`) — `useHoverReveal`'s `handleEnter` just returns early if `window.innerWidth` is under that, so the menu items fall back to being plain links (tap navigates immediately, no panel) on phone and tablet alike, rather than trying to make the desktop-shaped panel fit smaller geometry.

**Implementation notes:**
- The overlay line and reveal container are rendered **outside the `<nav>`/`<li>` tree entirely** (as siblings in the returned fragment, one `Fragment` per active hover, keyed by index) — not inside the hovered `<li>`. Reason: the `<li>` has the `slide-right` entrance animation (`animation: menu-slide-right-in ... both`), which includes a `transform`. Any CSS `transform` on an ancestor — even one just resolved/held via `animation-fill-mode: both` — creates a new *containing block*, making descendant `position: fixed` elements position relative to *that ancestor* instead of the viewport. That was the original cause of the line "disappearing" entirely. Keep this gotcha in mind anywhere else in the app: `position: fixed` is not reliably "fixed to the viewport" once *any* ancestor has a transform (animated or static).
- `width: 96%` (inherited from `.menu__item-line`) on an element that becomes `position: fixed` recomputes that percentage against the *viewport*, not the original narrow parent — `.menu__item-line--overlay` explicitly resets `width: auto` and `margin: 0` to avoid this.

**The "content finishes before panel collapses" pattern:** `useHoverReveal`'s second argument, `exitDelayMs`, delays setting `isActive` to `false` (which is what drives the panel's own collapse transition) until the panel's *content* has finished its own exit animation — otherwise the content visibly shrinks/clips mid-fade as the panel collapses underneath it. `hover0` (Featured Work) passes `FEATURED_EXIT_TOTAL_MS`, `hover1` (Photography) passes `PHOTO_EXIT_TOTAL_MS`; `hover2` (Information) passes `INFO_IMAGE_EXIT_DURATION_MS`. Only `isLeaving` (a separate piece of state, set immediately on mouse-leave, independent of the delayed `isActive`) drives which CSS animation class content gets — it does not affect the existing isFixed/isActive collapse timing/architecture from the previous fix, so this was additive and low-risk. If a 4th reveal item or a new animated content type is added later, follow this same pattern: compute its own total exit-animation time as a constant and pass it as `exitDelayMs`.

### Click-to-exit transition (added 2026-07-07)

Clicking any of the 3 menu links (`<a href="#">`, still not real routes — `e.preventDefault()`'d in `Menu.jsx`) now plays a "everything retreats off screen" transition, since the Featured Work / Photography / Information pages don't exist yet and this is meant to be the disappear-half of a future page transition:

- **State lives in `Home.jsx`**: `isExiting` (`useState`), flipped true via `onItemClick` passed down as a prop to `<Menu isExiting={isExiting} onItemClick={...} />`. `Menu` also receives/uses `isExiting` internally (it's a prop now, not a purely self-contained component — keep this in mind if `Menu` is ever reused elsewhere).
- **Direction is per-element, not a generic fade**: title (`home__title-text--exit`) and subtitle (`home__role--exit`) slide **up** (`translateY(-70px)`, `home-exit-up` keyframe in `Home.css`) while fading out; the menu (`menu--exiting` on `<nav>`, `menu-exit-right` keyframe in `Menu.css`) slides **right** (`translateX(90px)`) while fading out. This was an explicit correction from an initial plain fade+blur version (matching the entrance style) — the user wanted directional "hiding into the corners" instead, so don't revert to a shared fade-out keyframe without being asked.
- **Duration is 1s** for all of the above (bumped up from an initial 0.6s per user feedback that it felt too fast).
- **The hover overlay line + reveal panel also need to fade/slide with the menu** if the user clicks while actively hovering an item (panel open, photos visible) — these live *outside* `<nav>` (see the "outside the tree" gotcha above), so they don't inherit the nav's exit animation automatically. Fixed by giving them their own `menu__hover-exit` class (same `menu-exit-right` keyframe) applied whenever `isExiting` is true, alongside their existing `menu__item-line--overlay` / `menu__featured-reveal--{index}` classes. If a new hover-triggered element is added outside `<nav>` in the future, remember to also gate it on `isExiting` or it'll get left behind on screen.
- **Gotcha already hit once:** the subtitle's `animationDelay` (`SUBTITLE_DELAY_MS`, 1.5s — used only so the subtitle's *entrance* starts after the title's) was being applied unconditionally via inline `style`, so it was *also* delaying the subtitle's exit by 1.5s, making it lag far behind the title when leaving. Fixed by making that inline `animationDelay` conditional: `isExiting ? '0ms' : `${SUBTITLE_DELAY_MS}ms``. Any other element that reuses an entrance-only delay constant for both directions should get the same treatment.

### Mobile + tablet responsive layout (added 2026-07-14)

Before this, `.information` only had a desktop layout (a `flex` row: `.information__main` wrapping name/role/bio/specialties on the left, `.information__side` on the right) — below ~1180px it just rendered squished, unreadable. Requested order for mobile/tablet: **name → role → photo+socials → bio → specialties** (photo moved up, right after the role, instead of staying at the bottom or beside the text — reasoning: a visual portfolio should show the face/work quickly before asking someone to read a paragraph, and it mirrors Home leading with video before text).

**Grid, not flex, and no `.information__main` wrapper.** To get a *different* visual order per breakpoint from *one* DOM order, `.information__main` was removed entirely — name/role/`.information__side-wrap`/bio-wrapper/specialties are now direct children of `.information`, in that exact DOM order (which **is** the mobile order, verbatim). `.information` itself is `display: grid`:
- **Desktop:** `grid-template-columns: 1fr auto; grid-template-rows: repeat(4, auto);`. Name/role/bio/specialties auto-place into column 1 (rows 1–4); `.information__side` is explicitly placed at `grid-column: 2; grid-row: 1 / 5;` (spanning all 4 rows) — pulled into its own column regardless of where it sits in the DOM. `1 / 5` (not `1 / -1`) because grid's `-1` line only resolves against *explicit* row tracks — with only implicit rows it wouldn't reliably span to "the last one."
- **Mobile/tablet (`≤1180px`, matching the ceiling used everywhere else in this session — Menu's hover-reveal gate, Home's subtitle centering):** `grid-template-columns: 1fr;` — one column, so everything just falls into natural DOM order. No `order` property needed anywhere.

**Name + role centered and bigger on tablet specifically (768–1180px, matching `Menu.css`'s own tablet range — not the full ≤1180 mobile+tablet band used above):** `.information__name`'s `font-size` bumps from `clamp(3.5rem, 8vw, 7rem)` to `clamp(4.5rem, 11vw, 8rem)`, and both `.information__name`/`.information__role` get `text-align: center`. Phone (<768px) and desktop (>1180px) stay left-aligned at their existing sizes — this tablet-only centered/bigger treatment doesn't apply outside that band.

**`.information__side-wrap` — centering `.information__side` needed its own dedicated wrapper.** First attempt was `justify-self: center` directly on `.information__side` as a grid item of the single mobile column — this *should* work per spec, but visually it didn't (see the debugging story below for why that was hard to diagnose). The fix that actually shipped: wrap `.information__side` in `.information__side-wrap`, which is `display: contents` on desktop (removes its own box from layout entirely, so `.information__side` is still the real grid item at `grid-column: 2` — zero desktop impact) and becomes a real `display: flex; justify-content: center;` box only on mobile/tablet (`grid-column: 1`), directly centering its one child with plain flexbox instead of relying on grid `justify-self` sharing a cell with unrelated siblings. More explicit and easier to reason about/verify than the grid-item approach.

**Debugging story — the "more space on the left" reports were two separate, unrelated bugs, not one:**
1. **A recurring cascade-order bug, hit 3 times in this file** (`.information__role`'s font-size override, then `.information__side`'s `grid-column`, then `.information__specialties li`'s `justify-self`): each time, the `@media` override was placed *before* the element's own unconditional base rule elsewhere in the file. CSS cascade order applies **regardless of whether a rule is inside a media query** — at equal specificity, whichever rule is declared *later in the file* wins, media-scoped or not. So the base rule (declared later) was silently winning and undoing the earlier media-query override, even though the media query's condition was true. **Every responsive override in this file now has an explicit comment + is physically placed right after the base rule it modifies** — if adding a new one, follow that placement or it'll silently no-op exactly like these did.
2. **A false lead: `scrollbar-gutter: stable both-edges`**, added on `.information` alongside its `overflow-y: auto` safety net, with the (reasonable-sounding) theory that a scrollbar appearing only on the right was eating into the content box asymmetrically. This was **wrong** and made things *worse* — confirmed by actually measuring `getBoundingClientRect()` on `.information__side-wrap` via a headless Chrome + puppeteer-core script (temporary, removed after use — not a project dependency) at a 390px mobile viewport: with `scrollbar-gutter: stable both-edges` in place, left padding measured 47px vs. right padding 25.8px (should both be 32px, the resolved `clamp(2rem, 5vw, 5rem)` floor) — Chrome was not applying `both-edges` symmetrically despite what the spec says it should do. Removing that one line fixed it immediately: measured padding became exactly 32px/32px, and `.information__side`'s center landed exactly on the viewport's own center (195px of 390px). **If `.information` (or anything similar) ever needs `overflow-y: auto` again, don't reach for `scrollbar-gutter: stable both-edges` to "fix" asymmetry — it caused the exact asymmetry it was meant to prevent here.**

If a similar "is this actually centered" question comes up again and the CSS *looks* correct on review: don't keep guessing from static analysis — get real numbers. `getBoundingClientRect()` on the relevant elements via a quick headless-browser script (Chrome is installed at `C:\Program Files (x86)\Google\Chrome\Application\chrome.exe`; `npm install --no-save puppeteer-core` to drive it, since neither is a project dependency) settled in minutes what several rounds of pure code review couldn't.

**Specialty pills — 2-per-row on phone (≤768px), 3-per-row on tablet (768–1180px), centered — settled on `flex-wrap`, not Grid.** Grid (`display: grid; grid-template-columns: repeat(N, max-content)`) was the first approach and went through several rounds of fixes (documented in earlier history: `1fr` columns made pills look "fatter" by stretching each column to an equal share of the available width regardless of content — fixed by `max-content`, which sizes each column tightly to its widest occupant; `justify-self: center` on individual `li`s made a short pill shift inward relative to a longer one sharing its column — fixed by `justify-self: start`) — but Grid fundamentally **can't center an incomplete last row**, since every row shares the same column tracks, so a shorter trailing row (e.g. 2 pills left over from 5, under a 3-column grid) just sits flush left instead of centering as its own group. Flexbox's `justify-content: center` centers *each wrapped line independently*, incomplete or not, which is exactly what's needed — so this reverted to `flex-wrap` (closer to the original desktop behavior) with a `max-width` tuned per breakpoint to force the wrap at the right count for the current 5 `SPECIALTIES` strings: **320px** (phone, fits the first 2 pills' measured width but not a 3rd) and **500px** (tablet, fits the first 3 but not a 4th) — both measured via `getBoundingClientRect()`, not guessed. `.information__specialties` itself still needs `justify-self: center` too (same reason as `.information__side` above — as a grid item of `.information`'s own single column, it'd otherwise stretch full-width and its constrained-width flex box would sit flush left instead of centered). **Not generic** — if `SPECIALTIES` changes enough to shift these pill widths, both `max-width` values need re-tuning against the new content (the same measurement technique below), not assumed to still produce the same split. A `margin-top: 1rem` (≤1180px) adds extra breathing room above the pills specifically, on top of `.information`'s shared `row-gap: 1.4rem` — same technique as `.information__role`'s negative margin-top, just adding instead of removing.

**Photo — bigger on tablet only, phone unchanged.** `.information__side`'s `width` (base `clamp(180px, 18vw, 260px)`, tuned for sitting next to a full text column on desktop) gets a `(min-width: 768px) and (max-width: 1180px)` override bumping it to `clamp(300px, 42vw, 440px)` — tablet has the room since `.information__side` sits alone on its own row there (see `.information__side-wrap` above), so it can take up much more width. **Bento CSS Grid bug (fixed 2026-07-09):** the bento grid initially used `grid-template-rows: repeat(5, 1fr)`, which blew out row 3 to ~480px (vs. the intended ~239px) and pushed the last two rows off the bottom of the viewport with no way to scroll to them (`.photography` is `position: fixed`, so overflow just gets clipped by the viewport, not scrollable). Root cause: **`1fr` in CSS Grid is really `minmax(auto, 1fr)`**, and for a grid item that's a replaced element (an `<img>`) without an explicit height override, the `auto` minimum falls back to the image's *intrinsic aspect ratio* at the cell's resolved width — the two cells spanning 2 columns (`h`, `e`) needed ~480px of height to satisfy their natural aspect ratio at that width, so that row's `1fr` track got stretched to fit them, even though `width: 100%; height: 100%` was set on the `<img>`. Fixed by changing both `grid-template-columns`/`grid-template-rows` to `repeat(n, minmax(0, 1fr))` and adding `min-width: 0; min-height: 0;` on `.photography__bento-img`. **Remember this gotcha anywhere else in the app that grids/flexes photos:** always use `minmax(0, 1fr)` (or `min-width/min-height: 0` on the item) instead of a bare `1fr`/`flex: 1` when the grid/flex items are images or other replaced elements — otherwise their intrinsic aspect ratio can silently override the intended even split.

### Color system — centralized into CSS custom properties (added 2026-07-15)

Every color in the site used to be a hardcoded hex/rgba literal, repeated across 8 files (36 occurrences total) — e.g. `#1a1a1a` alone appeared as both a text color *and* a hover-fill background in 6+ different places. Centralized into `:root` custom properties in `src/index.css`, the one file every component's CSS can rely on being loaded first:
- Solid colors: `--color-cream` (`#f2efe9`), `--color-page-bg` (`#e8e6e6`), `--color-ink` (`#1a1a1a`), `--color-white`, `--color-black`.
- `--color-theme-dark` (`#111111`) / `--color-theme-accent` (`#c9622f`) — the 2 non-light face colors from `ThemeToggle`'s comparison harness specifically (see below), kept separate from `--color-ink`/`--color-cream` even though `--color-theme-dark` is visually close to `--color-ink` — they're conceptually different (site chrome color vs. a theme-preview swatch) and were already slightly different literal values (`#111111` vs `#1a1a1a`) before this refactor, so merging them would have been a visual change, not just a rename.
- `--rgb-white`/`--rgb-black`/`--rgb-ink`/`--rgb-cream` — raw `R, G, B` triplets (no `rgb()` wrapper) specifically so call sites can compose `rgba(var(--rgb-x), alpha)` at whatever opacity they need, since CSS can't extract channels from a hex custom property directly. Existing opacities were preserved exactly as they were (e.g. `rgba(0,0,0,0.35)` → `rgba(var(--rgb-black), 0.35)`) — this pass deliberately did **not** collapse the ~15 different black/white opacities scattered across shadows/borders into a smaller ramp, to keep it a pure refactor with zero visual change (confirmed via before/after screenshots of Home and Information).
- One real inconsistency fixed in passing: `ThemeToggle.css` had `#111111` in most places but `#111` in one (`.theme-toggle-picker__btn--active`) — same rendered color, just normalized to the one `--color-theme-dark` variable.
- `ThemeToggle.jsx`'s `THEME_COLORS` JS object was also switched from hardcoded hex to the string `'var(--color-cream)'` etc. — CSS custom property references work fine as plain strings in inline `style={{}}` values, so JS and CSS now read from the exact same source instead of keeping a second copy in sync by hand.
- This was groundwork only when first written — see "Dark theme" below for how switching was actually wired on top of it.

### Dark theme — live and working (added 2026-07-16)

`ThemeToggle` (see below) now actually switches the site's colors, not just its own preview. A `useEffect` in `ThemeToggle.jsx` sets `document.documentElement.setAttribute('data-theme', activeTheme)` on every click, and `src/index.css` has a matching override block:

```css
:root[data-theme='dark'] {
  --color-page-bg: var(--color-theme-dark);
  --color-ink: var(--color-cream);
  --rgb-ink: 242, 239, 233;
}
```

**Why this was so little code:** every section already read colors through `--color-page-bg` (background) and `--color-ink` (text) instead of hardcoded hex, so overriding just those two under `[data-theme="dark"]` flips Information, Photography, and the video-exit solid layer all at once — confirmed via screenshots, zero component-level changes needed anywhere else in the app.

**`--color-cream`/`--rgb-cream` are deliberately NOT touched by the dark-theme block** — they're reused by `CustomCursor`'s *light* variant (cream cursor, used on Home's dark video background), which shouldn't change with the site theme since Home's video is always dark regardless. Only `--color-ink`/`--rgb-ink` are inverted (to resolve to cream's *value*, without touching the cream variable itself).

**A nice side effect, not extra work:** `CustomCursor`'s `.custom-cursor--dark` variant (applied via the *section*-based `isLightSection` prop in `Home.jsx`, unrelated to the site theme) already reads `var(--color-ink)`/`var(--rgb-ink)` for its color — so under the dark site theme, on Information/Photography, that variable now resolves to cream instead of near-black, and the cursor automatically becomes a light cursor on what is now a dark background. No change to `CustomCursor` was needed; this fell out of the variable-based architecture for free. If this ever looks wrong, check `--color-ink`'s resolved value under the active `data-theme` before suspecting `CustomCursor` itself.

**One spot the initial pass missed: outline borders hardcoded to black instead of `--color-ink`.** `.information__back`/`.photography__back` (the "← Volver" button), `.information__specialties li` (the specialty pills), `.information__social-link`, and `.photography__pager-btn` all had `border: 1px solid rgba(var(--rgb-black), 0.3)` — a literal black tint regardless of theme. That reads fine in light theme (text is also near-black, so it happens to match), but in dark theme the text (`--color-ink`, now resolving to cream) goes light while the border stayed black-tinted, making it barely visible against the also-dark background. Fixed by switching all of these to `rgba(var(--rgb-ink), 0.3)`, so the border always tracks the same variable as the text color instead of a fixed black. **When adding new bordered elements to Information/Photography, use `--rgb-ink` for the border tint, not `--rgb-black`** — the two happen to look identical in light theme, which is why this was easy to miss the first time; the difference only shows up once dark/color theme is active.

`src/components/ThemeToggle/ThemeToggle.jsx` + `.css` — a small object bottom-left on every section (mirroring `Menu`'s bottom-right position on Home), switching the site between all 3 live themes: light, dark, and the accent color.

Both are scoped to the toggle's own icon only; the real site-wide theme colors in `index.css` are untouched.

**Mounted globally, not just on Home.** Like `CustomCursor`, it lives in `Home.jsx` as a sibling of `VideoBackground` (not nested inside it), so it persists across Home/Information/Photography. Originally built nested inside `VideoBackground`'s children with `position: absolute` (only visible on Home) — moved out to top-level `Home.jsx` with `position: fixed` and `z-index: 15` (clears Information/Photography's own `z-index: 5`) after being asked to make it appear everywhere.

**Hover-only tooltip naming what clicking does (added 2026-07-16, labels in English).** `.theme-toggle__tooltip` shows the *next* theme's label (`MODE_LABELS`: "Light mode"/"Dark mode"/"Color mode" — English, unlike the Spanish UI copy elsewhere such as Information/Photography's "← Volver") to the right of the icon, fading + sliding in on `:hover`/`:focus-visible` — the object alone doesn't obviously read as a theme switcher, but a permanently-visible label was explicitly rejected in favor of hover-only, to match the minimal-chrome approach used everywhere else in this project (same reasoning as `CustomCursor`'s "VIEW" hover-reveal). Always a dark `rgba(black, 0.6)` chip + cream text regardless of the active theme (not tied to the theme variables) — it needs to stay legible over any of the 4 possible backgrounds behind it (Home's video, and the light/dark/orange page backgrounds), so it deliberately supplies its own fixed-contrast backdrop instead of trying to invert with the theme.

**Locked to the "iris" concept, flat/2D, picker removed (settled 2026-07-16 after some back-and-forth).** A comparison harness (`STYLES`, switchable live via a temporary `.theme-toggle-picker` button row) originally held 4 cinema-themed 3D concepts — `reel3d` (spinning film-reel cross-section with sprocket holes), `clapperboard` (classic black/cream striped clapper that claps on click), `iris` (6-blade SVG camera aperture), `dial` (rotating conic-gradient color wheel with a fixed pointer notch). The very first attempt before any of these — a plain rounded-square triangular prism — was rejected outright ("queda muy mal") for not reading as cinema-themed at all, which is what prompted building these 4 named concepts instead. The user picked **iris**; the other 3 variants and `.theme-toggle-picker` were fully deleted (not kept in reserve).

**What shipped:** a 6-blade SVG camera aperture (`IRIS_BLADE_ANGLES`, same polygon-per-blade technique as `CustomCursor`'s discarded iris cursor concept, but here as a fixed small control rather than something following the mouse), blade fill = the active theme color (`THEME_COLORS`, referencing the CSS custom properties from "Color system" above). Clicking cycles `light → dark → color` and replays a quick scale-down/up "shutter snap" (`theme-toggle-iris-snap` keyframe, plain `scale(1) → scale(0.7) → scale(1)`) via remounting the `<svg>` with `key={clickKey}`, so the snap restarts every click regardless of whether the previous animation finished. **Deliberately flat/2D** — see the two reverted detours below before touching this again.

**Two things were tried after this and both reverted — don't redo either without being asked again:**
1. Adding real CSS 3D depth to the iris (`perspective` on `.theme-toggle`, a resting `rotateX(50deg)` tilt on the SVG, per-blade `translateZ(±6px)` via `style.transform` in the JSX, `transform-style: preserve-3d`) after the user noted the flat iris looked 2D. This technically worked (confirmed via computed-style/matrix3d checks and screenshots — the disc genuinely read as a tilted ellipse), but the user still didn't like the result.
2. Replacing the iris entirely with a solid sphere (`.theme-toggle__ball`) — roundness sold via layered inset box-shadows (dark shadow one corner, light highlight the opposite corner) rather than any 3D transform, spinning `rotateY` on click. This looked like a genuinely convincing 3D ball (confirmed via screenshots) — the single-axis tilt approach in attempt 1 reads as "a coin," while all-around bevel shading reads as "a sphere," which is *why* the ball convincingly looked 3D where the tilted iris didn't. But the user asked to go back to the original flat iris anyway ("dejalo como estaba la primera vez, en 2D") rather than keep the ball.
- **Net result:** the flat 2D iris from the very first "iris" pick is the final state. If a "make it 3D" or "make it a ball" request comes up again, the bevel/box-shadow technique from attempt 2 is proven to work well for spherical objects — reuse that approach rather than re-deriving it, but don't apply either 3D treatment unless explicitly asked again.

**Verification method: real headless-Chrome screenshots, not just code review** — used throughout building/comparing all 4 original concepts and both of the reverted 3D attempts (`npm install --no-save puppeteer-core` driving the system Chrome install at `C:\Program Files (x86)\Google\Chrome\Application\chrome.exe`, same as the Information/Photography responsive work; uninstalled again afterward since it's not a project dependency). One real bug this caught during the comparison phase: the `dial` variant rendered as literally nothing (just the pointer triangle, no visible disc) because `.theme-toggle__dial-wrap` was a `<span>` (inline by default) with `width/height: 100%` set — which has no effect on inline elements — confirmed via `getBoundingClientRect()` showing `{w:0, h:0}` before the fix. Moot now since `dial` was deleted, but the lesson (inline elements ignore width/height; get real numbers instead of guessing when something renders as "nothing") applies generally.

### Featured Work section (placeholder content, layout not yet locked in, added 2026-07-16)

**Layout: comparison harness, 4 concepts, not locked in yet — `LAYOUTS` in `FeaturedWork.jsx`, switchable via a temporary bottom-right `.featured-work-picker` (same throwaway-harness pattern as every other picker in this project).** All 4 share the same `PROJECTS` data and the same `ProjectCard` (thumbnail/overlay/play-button/caption) where applicable:
